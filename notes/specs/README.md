# Specs

A spec says what the app does. Usually moved from `notes/Goals.md`.

- Ask the user before writing or changing a spec. If the code and a spec disagree, ask.
- Behaviour, not implementation. No history, no type, function or file names. What must be
  said about implementation goes in an "Implementation notes" section at the end of the file.
- Simple English. Short, direct sentences and plain words: "has", not "offers". Prefer it over
  the repo's own terms: "selected", not "picked out".
- Leave out what is implied, such as the count of a list.
- Match the writing style of the spec files here.
- Before presenting edits, make one final pass and cut what can go without losing precision.
